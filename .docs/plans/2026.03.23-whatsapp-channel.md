# WhatsApp Channel via Baileys

## High Level Goal

Add WhatsApp as a messaging channel to VoiceCC using **Baileys** (open-source WhatsApp Web multi-device protocol library). Users link their WhatsApp account by scanning a QR code in the dashboard. For each agent, a WhatsApp group named `[VoiceCC] <agentId>` is automatically created. Users chat with specific agents by messaging in the corresponding group.

The implementation reuses the existing Python chat session infrastructure (`claude_session.py` + `/chat/send` endpoint). Baileys runs in the Node.js server layer and forwards messages to Python, collects the full SSE response, and replies via Baileys.

Heartbeat integration: agents have a new config field `outboundChannel: "call" | "whatsapp"` (default: `"call"`). When a heartbeat decides `shouldCall: true`, the system routes the action based on this config -- either placing a Twilio call (existing behavior) or sending the reason as a WhatsApp message to the agent's group.

Session continuity: Claude sessions still time out after 10 minutes of inactivity. But the `session_id` from each response is stored per group. When a new message arrives after timeout, a new `ClaudeSDKClient` is created with `resume=stored_session_id`, which reloads the full conversation history automatically via the Claude Agent SDK.

Text-only in v1 -- no media messages (images, voice notes, documents).

**Known risks:** Baileys is a reverse-engineered protocol. WhatsApp may throttle or ban accounts used for automated messaging. Users should use a separate phone number. Pin Baileys to an exact version in package.json (no `^` prefix) since the library has no stability guarantees.

## Important Technical Notes

### Session continuity via Claude SDK resume

The Claude Agent SDK's `ClaudeAgentOptions` accepts a `resume: string` parameter (a session ID). When provided, the SDK reloads the full conversation history from its internal JSONL storage at `~/.claude/projects/`. This avoids manually persisting and replaying messages.

**Important:** Verify that `ResultMessage` in the installed `claude_agent_sdk` version actually exposes a `session_id` field. If it does not, the implementer must find the correct attribute name or use an alternative approach (e.g., reading the latest session ID from the JSONL files on disk).

Flow:
1. `stream_message` yields a `ResultMessage` which contains `session_id`
2. The Python `/chat/send` endpoint includes `session_id` in the final SSE `result` event
3. The Node.js `whatsapp-message-handler.ts` extracts the session ID and stores it in `group-mappings.json` alongside the groupJid-to-agentId mapping
4. Next time a message arrives for that group, the handler passes `resume_session_id` to `/chat/send`
5. Python's `get_or_create_session` uses `resume=session_id` in `ClaudeAgentOptions` if provided
6. If resume fails (session file deleted, corrupted), fall back to creating a fresh session

### SSE collection for WhatsApp replies

WhatsApp cannot stream -- it needs a complete message. `whatsapp-message-handler.ts` consumes the full SSE stream from `/chat/send`, accumulates all `text_delta` events into a single string, and sends one WhatsApp reply when `result` arrives. If the stream contains an `error` event, send a user-friendly error message to the WhatsApp group. If the response exceeds WhatsApp's message size limit (~65,536 bytes), split into multiple messages. Use byte length (not character count) for the split to avoid issues with multi-byte characters.

### Concurrency: one message at a time per group

The Python `claude_session.py` has a `streaming` guard that rejects concurrent requests on the same session key with `ALREADY_STREAMING`. Currently in `server.py`, this error is raised inside the async generator *after* the StreamingResponse (HTTP 200) has already been returned, meaning the client sees an abruptly closed empty stream rather than an HTTP 409.

**Fix required in `server.py`:** Add a streaming check **before** creating the `StreamingResponse`. If `session.streaming` is `True`, return an HTTP 409 immediately. This makes the behavior predictable for all callers (browser chat and WhatsApp).

After this fix, `collectSseResponse` checks for HTTP 409 and signals the caller to send a "Still thinking, please wait..." reply. No queueing.

### JID normalization

Baileys uses `<number>:0@s.whatsapp.net` for the socket user ID but group message senders appear as `<number>@s.whatsapp.net`. The `shouldHandleMessage` function must strip the `:0` device suffix before comparing sender JID to own JID.

### Direct Python calls (no Node.js proxy)

The WhatsApp message handler calls Python `/chat/send` directly via `fetch`, bypassing `dashboard/routes/chat.ts`. The chat proxy validates device tokens, which don't apply to WhatsApp.

### Baileys reconnection and credential revocation

Baileys sessions can disconnect (phone goes offline, WhatsApp server restarts). `whatsapp-manager.ts` implements a reconnect loop with exponential backoff. The connection state is exposed via the status endpoint so the dashboard can show it.

**Permanent revocation:** When Baileys emits a `connection.update` with a disconnect error containing status code 401 or 515 (logged out / replaced by another device), the handler must delete the stored credentials at `~/.voicecc/whatsapp/` and set state to `disconnected` (not `qr_pending`). The user must re-enable WhatsApp and scan a new QR code.

### Credential storage

Baileys stores auth credentials via `useMultiFileAuthState` at `~/.voicecc/whatsapp/`. This matches the existing pattern of storing config at `~/.voicecc/`.

### Group ownership and safety

Baileys creates groups where the linked account is admin and only member. `shouldHandleMessage` filters out DMs, status broadcasts, messages from the bot itself (matched via `sock.user.id` after JID normalization), and messages from any JID other than the connected account. This prevents unintended interactions if someone is added to a VoiceCC group.

### Group lifecycle: leave, not delete

WhatsApp does not support deleting groups via the API. `syncGroupsForDeletedAgent` leaves the group. The empty group persists on the user's WhatsApp -- known WhatsApp limitation.

### Pending group sync on connect (duplicate detection)

When WhatsApp transitions to "connected" state, `whatsapp-manager.ts` triggers a full group sync via `syncAllGroups`. For each existing agent, if no group mapping exists, it first fetches the list of existing WhatsApp groups and checks if a group named `[VoiceCC] <agentId>` already exists (e.g., from a previous session). If found, it registers the mapping for that existing group instead of creating a duplicate. Only creates a new group if no match is found.

### Heartbeat outbound channel routing

When `shouldCall: true`, `heartbeat.py` checks the agent's `outboundChannel` config field:

- `"call"` (default): existing behavior -- `initiate_agent_call()` places a Twilio call with session handoff
- `"whatsapp"`: calls `send_whatsapp_message()` which POSTs to the Node.js server at `POST /api/whatsapp/send` with `{ agentId, text: reason }`. The Node.js handler resolves the agent's WhatsApp group from the mapping and sends the message via Baileys. No session handoff -- the user can reply in the group, which starts a normal WhatsApp chat flow.

The heartbeat JSON response (`{"shouldCall": true, "reason": "..."}`) remains unchanged. The routing is purely config-driven.

Note: `send_whatsapp_message()` calls the Node.js server (not Python) because Baileys runs in Node.js. This is the reverse of the normal flow where Node.js calls Python. The Python heartbeat -> Node.js WhatsApp -> Baileys path is straightforward since both servers run on localhost.

### Outbound channel validation

The `outboundChannel` selector in the agent dashboard always shows both options ("Phone Call" and "WhatsApp"), but disconnected channels are greyed out (disabled) in the dropdown:
- "Phone Call" is selectable when Twilio is running (`GET /api/twilio/status` returns `running: true`), greyed out otherwise
- "WhatsApp" is selectable when WhatsApp is connected (`GET /api/whatsapp/status` returns `status: "connected"`), greyed out otherwise

On the Python side, `heartbeat.py` also validates before acting: if `outbound_channel` is `"whatsapp"` but the `POST /api/whatsapp/send` call fails (WhatsApp disconnected), it logs a warning. It does NOT fall back to calling -- the user explicitly chose a channel and should know if it's not working.

### QR code rendering

The `GET /api/whatsapp/status` endpoint returns the raw QR code string from Baileys. The frontend `WhatsAppPanel.tsx` uses the existing `qrcode.react` dependency (already in package.json) to render it as an image. No server-side QR image generation needed.

### whatsapp-message-handler.ts (NEW)

Handles incoming WhatsApp messages: validates, routes to the correct agent, collects the Claude response, and sends the reply.

#### Types

```
WhatsAppIncomingMessage {
  groupJid: string
  senderJid: string
  text: string
  messageId: string
}
```

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `handleIncomingMessage` | `msg: WhatsAppIncomingMessage` | `Promise<void>` | Main handler. Resolves agentId from group mapping, gets lastSessionId for resume, calls Python `/chat/send` with `session_key: "wa:<groupJid>"`, `agent_id`, `resume_session_id`. Collects full SSE response via `collectSseResponse`. If ALREADY_STREAMING detected, replies "Still thinking, please wait...". Otherwise stores the returned session_id via `setLastSessionId` and sends reply via Baileys |
| `shouldHandleMessage` | `msg: proto.IWebMessageInfo, ownJid: string` | `WhatsAppIncomingMessage \| null` | Extracts text from a raw Baileys message. Normalizes JIDs (strips `:0` device suffix) before comparing. Returns null for: non-text messages, DMs (no groupJid), status broadcasts, messages from the bot itself, messages from JIDs other than `ownJid`, messages in unmapped groups |
| `collectSseResponse` | `response: Response` | `Promise<{ text: string, sessionId: string \| null }>` | Checks `response.ok` first -- on HTTP 409 (ALREADY_STREAMING), returns `{ text: "ALREADY_STREAMING", sessionId: null }`. On other non-2xx, throws. Reads the SSE stream (format: `data: {"type":"text_delta","content":"..."}\n\n`), accumulates `text_delta` events, extracts `session_id` from the `result` event. Returns the final text and session ID. On `error` SSE events, returns a user-friendly error message with null sessionId |
