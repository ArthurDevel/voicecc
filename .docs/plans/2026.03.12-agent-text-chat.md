# Agent Text Chat

## High Level Goal

Add a "Chat via Text" button on the AgentDetail page that opens a `/chat` page in a new tab (mirroring the `/call` pattern). The chat page connects to the agent via WebSocket and provides a text-based conversation UI. The user types messages, the server sends them to a Claude session (with the agent's SOUL.md, MEMORY.md, HEARTBEAT.md context), and streams text responses back.

The system prompt uses a **base + overlay** pattern: `system.md` is refactored into a base prompt with a `<<MODE_OVERLAY>>` placeholder. Two small overlay files (`system-voice-overlay.md` and `system-text-overlay.md`) are inserted at that placeholder depending on the session mode. This avoids maintaining duplicate prompts. All consumers of `system.md` (browser-server, twilio-server, heartbeat, claude-session fallback) are updated.

## Important Technical Notes

### Text chat skips the entire audio pipeline

The text chat path does **not** need: VAD, STT, TTS, AudioAdapter, endpointing, or narration. It creates a `ClaudeSession` directly (via `createClaudeSession`) and streams events over WebSocket as JSON. This makes it the simplest session type. However, it still needs a session lock (`acquireSessionLock`) because each chat session spawns a Claude Code subprocess that counts against `MAX_CONCURRENT_SESSIONS`.

### Concurrent message handling

The `streaming` flag on `ActiveChatSession` prevents processing a new user message while Claude is still responding. If a `user_message` arrives while `streaming` is `true`, the server sends back `{ type: "error", content: "Please wait for the current response to complete" }`. The frontend also disables the send button during streaming as a first line of defense.

### Session resource limits

Chat sessions spawn a Claude Code process each (same as voice). `chat-server.ts` calls `acquireSessionLock()` from `session-lock.ts` (the same mechanism used by `createVoiceSession`) to share the limit with voice sessions. If the lock cannot be acquired (limit reached), the WebSocket is closed with an error message. The lock is released in the cleanup handler when the WebSocket closes.

### Cleanup on disconnect

When a chat WebSocket closes (user closes tab, network drop, etc.), the cleanup handler must: (1) close the `ClaudeSession` (which kills the Claude Code subprocess), (2) release the session lock, (3) remove from `activeSessions` map. This mirrors the pattern in `browser-server.ts` lines 170-179, using a `cleaned` flag to prevent double-cleanup from concurrent close/error events.

### WebSocket message protocol (chat)

**Client → Server:**
```json
{ "type": "user_message", "text": "Hello" }
```

**Server → Client:**
```json
{ "type": "text_delta", "content": "Hi there!" }
{ "type": "tool_start", "content": "", "toolName": "Read" }
{ "type": "tool_end", "content": "" }
{ "type": "result", "content": "" }
{ "type": "error", "content": "error message" }
```

The client accumulates `text_delta` events into the current assistant message. On `result`, the message is finalized and input is re-enabled. `tool_start`/`tool_end` are shown as inline status indicators (e.g., "Reading file...").

### System prompt overlay pattern

The base `system.md` contains agent-generic instructions (file descriptions, working directory, periodic checks). The mode-specific behavior is injected via `<<MODE_OVERLAY>>`:

```
<<MODE_OVERLAY>>

## Your files
...
```

`buildAgentPrompt` in `prompt-builder.ts`:
1. Reads base `system.md` (cached at module level)
2. Replaces `<<MODE_OVERLAY>>` with the overlay content for the given mode
3. Loads agent via `getAgent(agentId)` and builds agent files block
4. Replaces `<<AGENT_DIR>>` and `<<AGENT_FILES>>` as before
5. Returns complete prompt string

This is consistent with the existing `<<AGENT_DIR>>` and `<<AGENT_FILES>>` placeholder patterns already used in `system.md`.

### Authentication flow for chat

The "Chat via Text" button on AgentDetail generates a pairing code server-side (reusing `POST /api/webrtc/generate-code`) and passes it as a URL parameter: `/chat?code=XXXXXX&agentId=Y`. The Chat.tsx page auto-pairs using this code on mount (same as Call.tsx does when opened from the QR modal). This means the user never sees a PIN input screen when clicking from the dashboard. Manual PIN entry is only shown as a fallback for returning devices with expired tokens.

### No markdown rendering in v1

Assistant messages use `white-space: pre-wrap` for display. This preserves formatting from Claude's responses (line breaks, indentation) without needing a markdown library or sanitization. Markdown rendering can be added later as an enhancement.
