# Add Deepgram as TTS/STT Provider

## Goal

Add Deepgram as an alternative TTS and STT provider alongside ElevenLabs. Users can select their preferred provider per-direction (TTS/STT independently) from the dashboard settings panel. The voice server reads the active provider from `.env` and instantiates the corresponding Pipecat service. No changes to the LLM layer, VAD, or audio transport.

## Important Technical Notes

### Provider selection and ElevenLabs key requirement

Currently `load_config()` raises `ValueError` if `ELEVENLABS_API_KEY` is missing. With Deepgram as an alternative, we must relax this: only require the API key for the *active* provider. The validation logic becomes:

```
if stt_provider == "elevenlabs" or tts_provider == "elevenlabs":
    require ELEVENLABS_API_KEY
if stt_provider == "deepgram" or tts_provider == "deepgram":
    require DEEPGRAM_API_KEY
```

This means a user can run purely on Deepgram without an ElevenLabs key (and vice versa).

### Deepgram STT is streaming, ElevenLabs STT is batch

Deepgram's Pipecat STT service uses a persistent WebSocket for real-time streaming transcription. ElevenLabs STT (Scribe) is batch -- it buffers audio and sends it all at once. This difference is transparent at the pipeline level because both implement Pipecat's `STTService` base class. Deepgram STT will produce `InterimTranscriptionFrame` in addition to `TranscriptionFrame`. The `StopPhraseProcessor` only acts on `TranscriptionFrame` (final transcripts), which is correct -- interim frames pass through untouched.

### Deepgram TTS sample rate

Deepgram TTS defaults to linear16. Verify at implementation time that the default sample rate matches the pipeline's `audio_out_sample_rate` (24kHz for WebRTC, 8kHz for Twilio via `TwilioFrameSerializer`). If it does not match, pass `sample_rate=` explicitly to `DeepgramTTSService`.

### Constructor signature normalization in twilio_pipeline.py

`twilio_pipeline.py` currently uses flat kwargs (`model=`, `voice_id=`) while `voice_pipeline.py` uses `settings=` wrappers for ElevenLabs services. Before extracting shared factories, normalize `twilio_pipeline.py` to use the `settings=` pattern to match `voice_pipeline.py`. Both patterns work, but the factory needs a single calling convention.

### Provider string validation

`load_config()` must validate that `STT_PROVIDER` and `TTS_PROVIDER` are one of `("elevenlabs", "deepgram")`. Raise `ValueError` immediately on invalid values rather than letting them propagate to the factory functions at pipeline start time.

### Deepgram STT aiohttp_session

The `create_stt` factory passes `aiohttp_session` to `ElevenLabsSTTService`. Verify at implementation time whether `DeepgramSTTService` accepts this parameter. If not, only pass it for the ElevenLabs branch.

### Provider selection persistence

The frontend's `selectTts`/`selectStt` handlers write `TTS_PROVIDER`/`STT_PROVIDER` via the existing generic `POST /api/settings` endpoint in `settings.ts`. No new write endpoint is needed in `providers.ts` -- the provider routes are read-only.

### Voice listing endpoints

`AgentDetail.tsx` calls `GET /api/providers/tts/${active}/voices` to populate the per-agent voice picker. This endpoint does not currently exist for any provider (pre-existing bug). Both must be implemented:

- `GET /tts/elevenlabs/voices` -- calls the ElevenLabs REST API (`GET https://api.elevenlabs.io/v1/voices`) using the stored API key. Returns `{ voices: Array<{ id, name }> }`.
- `GET /tts/deepgram/voices` -- Deepgram does not have a voice listing API. Return a hardcoded list of their current Aura voices (e.g. aura-asteria-en, aura-luna-en, aura-stella-en, aura-athena-en, aura-hera-en, aura-orion-en, aura-arcas-en, aura-perseus-en, aura-angus-en, aura-orpheus-en, aura-helios-en, aura-zeus-en). This is acceptable because Deepgram's voice list changes infrequently.

Both endpoints should return `{ voices: [] }` with a 200 if the API key is not configured, rather than erroring.

### AgentDetail.tsx provider-aware voice picker

Line 130 hardcodes `const providerKey = activeProvider as "elevenlabs"`. This must use `activeProvider` directly as the key (typed as `keyof AgentVoiceConfig`). The label on line 378 also hardcodes "ElevenLabs voice" -- it should use the active provider's display name.

### Dashboard active provider read

The `/tts` and `/stt` endpoints currently hardcode `active: "elevenlabs"`. They must read `TTS_PROVIDER` and `STT_PROVIDER` from `.env` (defaulting to `"elevenlabs"` for backwards compatibility).

5. Running with only an ElevenLabs key (no Deepgram key) continues to work as before (backwards compatible)
6. All existing tests pass; new tests for provider endpoints pass

9. Voice listing endpoints return voices for both ElevenLabs and Deepgram
