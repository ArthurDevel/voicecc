# Chat Session Resume

## High Level Goal

When a user leaves a browser chat tab idle and returns after the 10-minute Python session timeout, the conversation resumes seamlessly. Claude reloads the full conversation history from its persisted JSONL file via the SDK's `resume` option, so the user never experiences amnesia.

Additionally, users can resume any past conversation from the dashboard history by clicking into it.

The fix threads the Claude `sessionId` (returned in each SSE `result` event) through the entire stack:

1. Frontend captures it and stores it in a ref + URL query param
2. Frontend sends it with every `/api/chat/send` request
3. Node proxy forwards it to Python (fixing the current data loss where the proxy strips this field)
4. Python passes it as `resume_session_id` when recreating an expired session

No Python changes are needed -- the backend already supports `resume_session_id`.

## Important Technical Notes

### URL as source of truth for session identity

The `sessionId` query param serves two purposes:
1. **Same-tab resume**: When the user returns after idle timeout, the frontend reads `sessionId` from its ref (populated from the last `result` event). On next message send, it includes `resumeSessionId` in the POST body. If the Python session is still alive, the resume ID is ignored (existing session is reused). If expired, a new `ClaudeSDKClient` is created with `resume=sessionId`.
2. **Cross-tab resume**: From the conversation history view, a "Resume" button links to `/chat?agentId=X&sessionId=Y`. The Chat component reads `sessionId` from URL on mount and uses it for the first message.

The URL is updated via `window.history.replaceState` (not React Router navigation) to avoid re-renders. The `replaceState` call builds a clean URL with only relevant params (`agentId`, `sessionId`), stripping ephemeral params like `code` used during pairing.

### Session ID lifecycle

- `sessionId` is `null` until the first `result` SSE event arrives
- Each `result` event may return a new `sessionId` (Claude SDK may rotate IDs)
- The frontend always stores the most recent one and uses it for the next request
- If the user opens a fresh `/chat` with no `sessionId` param, the first message creates a brand new session (current behavior preserved)

### Resume works from disk, not memory

The Claude SDK `resume` option reads conversation history from persisted JSONL files on disk, not from the in-memory Python session. This means resume works even after:
- The 10-minute inactivity timeout destroys the in-memory session
- The user explicitly closes a tab (which triggers `close_session` via `sendBeacon`)
- The Python server restarts

This is important: even if a close and resume race (user closes tab, immediately clicks Resume from history in another tab), the resume will succeed because it reads from the JSONL file.

### Remove sendBeacon close on unmount

The current Chat.tsx unmount effect fires `POST /api/chat/close` via `sendBeacon`, which explicitly destroys the Python session. This is unnecessary now that sessions auto-expire after 10 minutes of inactivity. Removing it avoids premature session destruction that would force unnecessary resumes. The inactivity cleanup timer is sufficient.

The `/close` route in `chat.ts` and `server.py` is kept -- it is still useful for manual cleanup and may be called by other channels (WhatsApp, voice). Only the frontend `sendBeacon` caller is removed.

### Pre-loading conversation history on resume

When `sessionId` is present in the URL on mount (resume scenario), the Chat component fetches the conversation history from `/api/conversations/{sessionId}?agentId={agentId}` and populates the messages list. This way the user sees the full past conversation, not a blank chat. Claude also has the full history (via SDK resume), so both sides are in sync.

Important details:
- **Message format mapping**: The conversations API returns `ConversationMessage` (role: user/assistant/tool_use/subagent, ISO timestamp, no id/isStreaming). These must be mapped to `ChatMessage` format (role: user/assistant/tool, numeric timestamp, generated id, isStreaming: false). `tool_use` maps to `tool` (content = toolName). `subagent` messages are dropped (they are tool-level detail).
- **Skip when agentId is missing**: The conversations endpoint requires `agentId` (returns 400 without it). If `agentIdRef` is falsy, skip the history pre-load entirely -- the user will see a blank chat but Claude still resumes via the SDK.
- **Guard against race with user input**: If the user sends a message before the history fetch completes, the fetch result should be discarded (use an abort controller or a stale flag). Do not overwrite messages that were added while fetching.
- **Error handling**: If the history fetch fails (404, network error), silently continue -- the chat still works, the user just sees a blank history. Log the error to console.

### agentId mismatch on resume

Known limitation: if a user manually edits the URL to resume a session with a different `agentId` than the original, the system prompt will not match the conversation history. This is an edge case we accept -- the `agentId` in the URL should match the original session.

## Success Criteria

- Sending a message after the 10-minute timeout resumes the conversation with full history
- The URL updates to include `sessionId` after the first response
- Opening `/chat?sessionId=X&agentId=Y` directly resumes that conversation and shows past messages
- Conversation history view has a "Resume" button that opens a live chat for that session
- No changes needed on the Python side
- Existing fresh chat flow (no sessionId) still works identically
- The sendBeacon close on unmount is removed
