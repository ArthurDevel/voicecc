# Turn Detection & Interruption: Options Comparison

## The Problems

1. **Agent starts too fast**: User pauses mid-thought, VAD fires SPEECH_END, system immediately treats it as turn-complete. No "is the user actually done?" check.
2. **Interruption too slow**: 1500ms (browser) / 2000ms (Twilio) of sustained speech required before the system stops the agent. User has to talk over the agent for a long time.

## Current Architecture

- Silero VAD v5 (avr-vad) fires SPEECH_END after internal debounce
- Endpointing: 2+ words = instant completion; Haiku fallback disabled; effectively VAD silence = done
- Interruption: timer-based, SPEECH_START during SPEAKING triggers countdown

---

## Option 1: Pipecat Smart Turn v3.1 (audio-only)

**What it is**: Whisper Tiny encoder + linear classifier head, trained on conversational speech to predict end-of-turn from raw audio waveform.

| Aspect | Detail |
|---|---|
| Type | Audio-only (no transcript needed) |
| Model size | 8.68 MB (int8 ONNX) / 32.4 MB (fp32) |
| Parameters | ~8M |
| Latency | 10-65ms depending on hardware |
| Input | 16kHz mono PCM, up to 8 seconds |
| Languages | 23 |
| License | BSD 2-Clause (fully open) |
| Runtime | ONNX Runtime |
| Repo | https://github.com/pipecat-ai/smart-turn |
| HuggingFace | https://huggingface.co/pipecat-ai/smart-turn-v3 |

**How it detects turn completion**: Analyzes "grammar, tone and pace of speech, and various other complex audio and semantic cues" directly from the waveform. Outputs a binary classification: turn complete vs. not complete.

**Integration path**: Run ONNX Runtime in Node.js. On each SPEECH_END from VAD, feed the last N seconds of audio to Smart Turn. If it says "not complete", keep listening. If "complete", proceed.

**Pros**:
- Works on raw audio, no dependency on transcript quality
- Captures prosodic cues (intonation, pace) that text models miss
- Very fast (10-65ms) -- adds negligible latency
- Small model, BSD licensed
- Production-proven (used in Pipecat/Daily.co voice agents)

**Cons**:
- Binary output (no confidence score documented)
- No conversation context -- only looks at the audio waveform
- Relatively new (v3 released late 2025)

## Option 2: LiveKit Turn Detector (text-based)

**What it is**: SmolLM2-135M fine-tuned on conversational transcripts to predict end-of-turn from text.

| Aspect | Detail |
|---|---|
| Type | Text-based (requires ASR transcript) |
| Model size | ~135M parameters, quantized ONNX available |
| Latency | Not publicly benchmarked |
| Input | Last 4 turns of conversation text |
| License | LiveKit Model License (restrictive, NOT fully open) |
| HuggingFace | https://huggingface.co/livekit/turn-detector |

**How it detects turn completion**: Uses conversation context (last 4 turns) + current transcript. Outputs confidence score that the current text is end-of-turn. This score dynamically adjusts the VAD silence timeout -- high confidence = short wait, low confidence = long wait.

**Integration path**: Run ONNX model in Node.js. On each SPEECH_END, feed transcript + conversation history. Use output to decide whether to wait longer or proceed.

**Pros**:
- Uses conversation context (understands "I want to..." is incomplete)
- Confidence score allows dynamic thresholding
- The "adjust silence timeout" pattern is elegant

**Cons**:
- Restrictive license (not fully open source)
- Text-only -- misses prosodic cues entirely
- Depends on transcript quality
- 135M parameters is heavier than Smart Turn
- Requires maintaining conversation text history

## Option 5: Voice Activity Projection / VAP (audio-based)

**What it is**: Transformer model from KTH Stockholm that predicts turn-taking by projecting future voice activity for both speakers.

| Aspect | Detail |
|---|---|
| Type | Audio-only (stereo -- needs both speaker channels) |
| Parameters | ~1-5M (estimated, not documented) |
| Latency | 12-15ms per frame on CPU |
| Input | 16kHz stereo PCM (one channel per speaker) |
| Output | Probability distribution over 256 states for next 2 seconds |
| License | Open source |
| Repo | https://github.com/ErikEkstedt/VoiceActivityProjection |
| Real-time | https://github.com/inokoj/VAP-Realtime |

**How it works**: Predicts which speaker will talk next, including shift vs. hold, upcoming backchannels, and utterance length. Uses self-supervised learning on conversational data.

**Integration path**: Run as Python sidecar process (TCP/IP communication). Feed stereo audio (user channel + agent TTS channel). Read turn predictions.

**Pros**:
- Purpose-built for conversational turn-taking
- Predicts multiple event types (shift, hold, backchannel)
- Rich output (2-second projection window)
- No transcript needed

**Cons**:
- Requires stereo audio (separate speaker channels) -- significant architectural change
- No ONNX export, PyTorch only
- No Node.js bindings, requires Python sidecar
- Research-grade, not production-hardened
- CPC encoder dependency (Facebook Research)

## Option 6: SpeculativeETD (hybrid, two-tier)

**What it is**: A two-tier architecture with a tiny on-device model + a larger server model.

| Aspect | Detail |
|---|---|
| On-device model | 1M-parameter GRU, real-time |
| Server model | 94M-parameter Wav2Vec 2.0 base |
| Input | Audio |
| Paper | https://arxiv.org/abs/2503.23439 |

**How it works**: The tiny GRU runs continuously and detects likely end-of-turn. The larger Wav2Vec model verifies the prediction. If both agree, the turn is complete. This is the "speculative execution" pattern applied to turn detection.

**Pros**: Best of both worlds -- fast first-pass, accurate verification.
**Cons**: Very new (2025 paper), no production implementation available, two models to manage.

---

## Option 7: Re-enable Haiku semantic check (what we already have)

Our endpointing.ts already has a Haiku fallback path that's currently disabled. Re-enabling it with conversation context could help.

| Aspect | Detail |
|---|---|
| Latency | ~200ms (API call) |
| Cost | Haiku API usage per turn |
| Already built | Yes, just needs `enableHaikuFallback: true` |

**Improved version**: Instead of naive "is this a complete turn?", provide conversation context and the transcript. "Given this conversation so far, has the user finished their thought?"

**Pros**: Zero new dependencies, already partially implemented.
**Cons**: 200ms latency per turn, API cost, network dependency, no prosodic awareness.

## Recommendation

**For end-of-turn**: Combine **Smart Turn v3.1** (audio) + **Turnsense or re-enabled Haiku** (text).

- On SPEECH_END, run Smart Turn on the audio buffer (10-65ms)
- If Smart Turn says "complete" -> proceed immediately
- If Smart Turn says "not complete" -> wait for more speech, or run a quick text check as tiebreaker
- This gives you prosodic awareness (catches "I want to..." trailing intonation) AND keeps latency low

**For interruption**: Implement **two-stage interruption**:

- Stage 1 (100-200ms): Duck agent audio volume by 80% on SPEECH_START
- Stage 2 (500-800ms): Full stop if speech continues

This doesn't require a model -- it's a UX pattern change that gives the user immediate feedback.

# Interruption / Barge-In Detection

## Current Interruption Architecture

- During SPEAKING state, VAD fires SPEECH_START -> timer starts (1500ms browser / 2000ms Twilio)
- If speech sustains past threshold -> full interrupt (stop TTS + cancel Claude)
- If SPEECH_END before threshold -> false alarm, discard audio
- No distinction between intentional interruption, backchannel ("uh huh"), or noise
- No false-interruption recovery (once interrupted, the response is gone)

## The Backchannel Problem

"uh huh", "yeah", "okay" during agent speech are NOT interruptions -- they signal the user is listening. Our current system treats any sustained speech (>1.5s) as interruption. Short backchannels (<1.5s) are discarded, but longer affirmations or thinking-out-loud can trigger false interrupts.

---

## Interruption Option 1: Deepgram Flux (unified ASR + turn detection)

**What it is**: A single model that fuses speech recognition and turn detection. Replaces the entire VAD+STT+endpointing pipeline.

| Aspect | Detail |
|---|---|
| Type | Unified ASR + turn detection |
| End-of-turn latency | ~260ms |
| False interruption reduction | ~30% vs. pipeline approaches |
| Events | StartOfTurn, EndOfTurn, EagerEndOfTurn, TurnResumed |
| Config | `eot_threshold` (default 0.7), `eot_silence_threshold_ms` (default 5000ms) |
| Provider | Deepgram (cloud API) |

**How it handles interruption**: A `StartOfTurn` event during agent speech = barge-in. Also has `EagerEndOfTurn` (medium confidence, 150-250ms earlier) for speculative response generation, with `TurnResumed` to cancel if the user continues.

**Pros**:
- Solves both end-of-turn AND interruption in one model
- 30% fewer false interruptions
- No separate VAD/STT/endpointing pipeline to maintain
- Speculative processing built in (EagerEndOfTurn + TurnResumed)

**Cons**:
- Cloud dependency (Deepgram API)
- Replaces our entire pipeline -- large architectural change
- Vendor lock-in
- Pricing per audio minute

---

## Interruption Option 2: Amazon-style Barge-In Classifier (research)

**What it is**: Supervised classifier that distinguishes true barge-in from false barge-in using audio features + dialog context (Interspeech 2022, AWS AI Labs).

| Aspect | Detail |
|---|---|
| Type | Audio + dialog context |
| Architecture | Self-supervised speech representations + contextual features |
| Improvement | 5.7% relative F1 over baseline |
| Paper | Contextual Acoustic Barge-In Classification (Interspeech 2022) |
| Availability | NOT open-sourced |

**How it works**: Uses low-level speech representations from a self-supervised model (no ASR needed for core classification), infuses lexical information into speech representations, adds dialog state context. Classifies each barge-in event as true or false.

**Pros**: Dedicated to exactly our problem, uses both audio and context.
**Cons**: Not open-sourced, would need to train our own version.

---

## Interruption Option 3: LiveKit-style False Interruption Recovery

**What it is**: Not a model -- a UX pattern. If an "interruption" produces no transcribed words within a timeout, treat it as false and resume the agent's response.

| Aspect | Detail |
|---|---|
| Default interruption threshold | 0.5 seconds (vs. our 1.5s) |
| False interruption timeout | 2.0 seconds |
| Behavior on false alarm | Agent resumes from where it left off |
| Config | `min_interruption_duration`, `min_interruption_words`, `resume_false_interruption` |

**How it works**:
1. User speech detected during agent output -> pause agent after 0.5s
2. If no transcribed words within 2s -> emit `agent_false_interruption`, resume playback
3. If real words detected -> commit to interruption, cancel response
4. Conversation history is truncated to only include what the user actually heard

**Pros**:
- No model needed, purely logic
- Recovers gracefully from false alarms
- Lower threshold (0.5s vs our 1.5s) because recovery is safe
- History truncation prevents hallucination about unheard content

**Cons**:
- Requires buffering agent audio for potential resume
- Brief pause is still audible to user during false alarms
- Doesn't distinguish backchannel from noise

---

## Interruption Option 4: Two-Stage Volume Ducking

**What it is**: Split interruption into immediate feedback (volume duck) and confirmed action (full stop).

| Stage | Timing | Action |
|---|---|---|
| Stage 1 | 100-200ms after SPEECH_START | Duck agent volume by 80% |
| Stage 2 | 500-800ms sustained speech | Full stop (cancel TTS + Claude) |

**How it works**: On first SPEECH_START during SPEAKING state, immediately reduce agent volume. User gets instant feedback that the system heard them. If speech continues, fully interrupt. If speech stops, restore volume and continue.

**Pros**:
- Instant user feedback (100-200ms vs. current 1500ms)
- No model needed
- Graceful -- brief sounds don't kill the response
- Works with any transport (browser AudioWorklet can scale gain)

**Cons**:
- AudioWorklet needs modification to support gain control (currently only clear)
- The "ducked" state may sound odd if it happens frequently
- Still no backchannel awareness

---

## Interruption Option 5: DuplexCascade Micro-Turn Tokens (research)

**What it is**: A VAD-free cascaded ASR-LLM-TTS pipeline that uses special tokens to classify user behavior during agent speech.

| Token | Meaning | Action |
|---|---|---|
| `<user backchannel>` | User said "uh huh", "yeah" etc. | Ignore, keep talking |
| `<user is thinking>` | User is silent after agent finished | Wait, take no action |
| `<system backchannel>` | System should acknowledge | Play pre-recorded "mm-hmm" |

**Pros**: Explicit backchannel-vs-interruption distinction at the model level.
**Cons**: Research paper (March 2025), no production implementation. Requires a ~0.5B parameter LLM fine-tuned for control tokens.

---

## Interruption Option 6: Vapi-style Word Count Threshold

**What it is**: Only interrupt after the user has said N words, not just sustained audio.

**How it works**: Instead of a pure duration threshold, require `min_interruption_words` (e.g., 2-3 words) before committing to interruption. Short backchannels ("yeah", "okay") are 1 word and get filtered. "Stop, I want to change..." is 2+ words and triggers interruption.

**Pros**:
- Simple to implement (we already have STT running)
- Effectively filters single-word backchannels
- No model needed

**Cons**:
- Adds STT latency to interruption detection
- Single-word interruptions ("stop!", "wait!") would be missed
- Depends on transcript accuracy during overlapping audio

## How Production Platforms Compare

| Platform | Interruption Threshold | Backchannel Handling | Recovery | Method |
|---|---|---|---|---|
| **Our system** | 1500ms / 2000ms | None (discarded if <threshold) | None | Duration timer |
| **LiveKit** | 500ms | Via `min_interruption_words` | Yes (resume after 2s) | Duration + word count |
| **Pipecat** | VAD-driven (~150-200ms) | Via Smart Turn model | Pipeline cancellation | System frames |
| **Vapi** | Configurable word count | Custom backchannel model | Tracks cutoff point | Word count + model |
| **OpenAI Realtime** | 500ms silence, 0.5 VAD threshold | None documented | Truncates history | VAD threshold |
| **Deepgram Flux** | ~260ms (model-based) | Integrated in model | EagerEndOfTurn + TurnResumed | Unified model |

## AEC Dependency

Echo cancellation quality is foundational for interruption detection. Without it, the agent's own TTS bleeds into the mic and VAD can't distinguish user speech from echo.

- **Browser**: getUserMedia provides AEC -> lower threshold possible (1500ms currently)
- **Twilio**: No VPIO echo cancellation -> higher threshold needed (2000ms currently)
- Improving AEC would allow lowering both thresholds regardless of other changes

---

## Interruption Recommendation

**Quick wins (no model, implement now):**
1. **LiveKit-style false interruption recovery** -- lower threshold to 500ms, but resume if no words transcribed within 2s. Requires buffering TTS audio for potential replay.
2. **Word count gate** -- require 2+ transcribed words before committing to interruption. Filters "yeah"/"okay" backchannels.

**Medium-term:**
3. **Two-stage volume ducking** -- immediate user feedback at 100-200ms, full stop at 500-800ms. Needs AudioWorklet gain control.

**Longer-term:**
4. **Deepgram Flux** as full pipeline replacement -- solves both end-of-turn and interruption, but large architectural change.
